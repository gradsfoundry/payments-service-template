# Student sandbox — AWS resource design

What actually gets deployed to AWS, per student, and why. Companion to
`business-model.md` §7.2–7.3 (which sets the *principles* — no console
access, git-triggered, namespaced not per-account) — this is the
resource-level design that principle turns into.

## The gap this closes

The original `.github/workflows/ci-cd.yml` assumed a Lambda function
already existed and just called `update-function-code`. Two problems,
found while designing this end to end:

1. **Nothing ever created the function, the ECR repo, or the IAM role
   in the first place.** There was no answer to "what creates these
   the first time a student pushes?"
2. **A plain Express app doesn't run on Lambda as-is.** `server.js`
   calls `app.listen()` and waits for TCP connections — Lambda invokes
   a function per-event, it doesn't keep a socket open. Without a
   translation layer, the deploy would "succeed" and the app would
   never actually respond to a request.

Both are fixed below.

## Per-student resource inventory

One of each, named from that student's GitHub repo name (`{repo}` below
— e.g. `aishwarya-orders-api`), created automatically by that student's
own first pipeline run:

| Resource | Name | Purpose |
|---|---|---|
| ECR repository | `gradsfoundry/{repo}` | Holds that student's Docker images only |
| IAM role | `gradsfoundry-{repo}-deploy` | What their CI assumes via OIDC — scoped to only their own ECR repo + Lambda function |
| Lambda function | `gradsfoundry-{repo}` | Runs their container image — this *is* the live sandbox |
| Lambda Function URL | (auto-generated by AWS) | Public HTTPS endpoint — no API Gateway needed |
| CloudWatch Log Group | `/aws/lambda/gradsfoundry-{repo}` | Created automatically by Lambda; this is what the health-check/monitoring work (checklist Phase 2) reads from |

Nothing here is shared between students except the ECR *namespace*
prefix and the underlying AWS account — each student's role can only
touch resources whose name starts with `gradsfoundry-{their-own-repo}`,
enforced by IAM resource ARN conditions, not just convention.

## The Lambda Web Adapter fix

Rather than rewrite `server.js` as a Lambda handler (which would make
the app stop being "just a normal app" — bad for the whole "this feels
like a real job" premise), the `Dockerfile` now includes the
[AWS Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter):
a small extension, copied in as a layer, that proxies Lambda Function
URL requests to the app's normal HTTP port. The app code is unchanged —
it still just calls `app.listen(process.env.PORT)`. This only activates
inside an actual Lambda execution environment; running the same image
with plain `docker run` behaves exactly as before (verified locally).

## Identity model — two tiers, not one

**Tier 1 — one shared "provisioner" trust, scoped per student repo.**
Every student's CI workflow assumes *their own* IAM role
(`gradsfoundry-{repo}-deploy`), trusted via GitHub OIDC with a condition
that only *that exact repo* can assume it (`token.actions.githubusercontent.com:sub`
= `repo:gradsfoundry/{repo}:ref:refs/heads/main`). That role's
permissions are scoped by resource-name prefix, so even a student who
reads their own CI logs and finds their role ARN can't use it to touch
anyone else's Lambda function or ECR repo.

This role is created **once per student**, by you, via
`infra/provision-student.sh` — not hand-crafted in the console, and
not something a student does themselves (they don't have AWS access at
all, by design — §7.2). It's a batchable script, not "manual
provisioning" in the sense the plan was trying to avoid: you're not
touching the console per student, you're running one command per
student (or looping a CSV of usernames).

**Tier 2 — the student's own first CI run creates their actual
resources.** The pipeline now checks whether its ECR repo and Lambda
function exist and creates them if not (`aws ecr describe-repositories
|| aws ecr create-repository`, same pattern for Lambda). This is the
"self-service, git-triggered" part from §7.3 — the *resources* come
into being from the student's own push, only their *identity* (the IAM
role) was set up ahead of time.

**Why not fully dynamic identity too** (a single shared role every
repo could assume, scoped purely by naming convention)? IAM can't
cleanly express "this caller may only create/modify resources whose
name matches a substring of the caller's own identity" without the
caller's identity being externally asserted first — which is exactly
what the per-repo OIDC trust condition already does. Splitting it this
way is simpler to reason about and to audit than trying to make one
mega-role safe for 30 mutually-untrusted students.

## Teardown

A separate, narrower IAM role (`gradsfoundry-teardown`), trusted only
by a dedicated ops repo (not student-writable), with permissions
limited to `Delete*` actions on `gradsfoundry-*`-prefixed resources.
`infra/teardown.yml` runs on a schedule, lists repos in the org via the
GitHub API, and deletes any student's Lambda function + Function URL +
ECR repo once they've been inactive past a threshold or the cohort has
ended. See that file for the exact logic.

## Cost tracking

Every resource gets tagged `gradsfoundry:cohort=<id>` at creation. One
AWS Budget (not per-student) filters on that tag, so cost is visible
and alertable in aggregate without provisioning 24+ separate budgets.
Cost-allocation tags need a one-time toggle in the Billing console and
can take up to 24h to start appearing — do this before the first
cohort, not the week of.

## What's still open

- Exact IAM policy JSON for the per-student role and the teardown role
  — drafted in the two scripts below, not yet tested against a real
  account (no AWS account exists yet).
- Whether `provision-student.sh` runs as a one-by-one command or reads
  a CSV of a cohort's GitHub usernames — either works; CSV is more
  pleasant at 15-30 students.
